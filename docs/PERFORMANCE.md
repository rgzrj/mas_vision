本页合并原2026-11-07/08交接文档中仍有价值的测速、模型精度边界、MAS/SP/RMCS/深大对比和论文来源。编译、环境准备与运行命令以[README_LINUX.md](../README_LINUX.md)为准，当前分层见[结构说明](CODE_STRUCTURE_AUDIT_20261109.md)。

## 测量口径

Process FPS为实际生产者处理吞吐，不等于SDL/Rerun/远程桌面上屏率。纯推理infer/s不包含预处理、采集、跟踪、火控、输出与显示；performance.csv的result_age_ms截止结果进入同步记录阶段前，不含串口送达或上屏。无目标时track/shoot耗时接近零不能代表真实跟踪场景。

下方数据均保留原测量日期和条件，不是本轮整理后重新测出的性能。INT8的FP32输入输出不代表内部算子仍是FP32；模型速度也不能替代三类五点及预测精度验收。

auto_buff/buff_detect/yolo/model/rune_szu.onnx 是原 FP32 基准；rune_szu_public_int8.xml 和同名 .bin 是公开视频量化试验。XML/BIN 必须同目录。

### 11 月 8 日：独立 Python 编译属性查询

用户按 LATENCY / 单流 / 6 线程重建 CPU compiled model，结果为：available_devices=['CPU']，INFERENCE_NUM_THREADS=6，NUM_STREAMS=1，SCHEDULING_CORE_TYPE=ANY_CORE，ENABLE_CPU_PINNING=True，ENABLE_HYPER_THREADING=False，INFERENCE_PRECISION_HINT=float32。这不是直接读取正在运行的 C++ 进程属性。ANY_CORE 是允许的调度策略，不证明实际每次使用了 P 核或 E 核；CPU-only 枚举也不证明硬件没有核显。精度提示不等于逐算子执行精度。

新增 `tools/benchmark_cpu_scheduling.py`，固定 6 线程、单流、开启绑核、关闭超线程，用 ANY / PCORE / PCORE / ANY 顺序测试同一 FP32 模型。每组预热 20 次、默认测 200 次同步 infer，输入固定且在计时外准备，输出均值、P95/P99、实际编译属性、模型 SHA 和 JSON。运行时停止实机程序；此测试不包含取图、预处理、track/shoot、显示或串口，不把 infer/s 当作实机 FPS。

# 在 Linux build/ 内；先将脚本放到项目 tools/。

脚本已用本地 Windows OpenVINO 2026.4.1 和原模型做 5 次/组的功能检查，四组均可完成；该小样本和本机性能不用于判断目标 Linux 上 PCORE_ONLY 是否更快。只有目标机对照显示稳定收益后，才改生产 compile_model 属性并复测实机与显示负载。

### 11 月 8 日：指定公开 test_video.avi 的 INT8 试验候选

## 5. Rerun 开销与固定滞后如何处理

当前已有 SDL 后端：display.backend=sdl，不启动 Viewer；在显示尺寸上绘制 BGR 图，再直接上传纹理，绕过原 JPEG 与整幅透明 PNG 编码。彩色文字、FPS、原始点及预测保留；主线程轮询 SDL，后台整组发布同帧视图，只保留最新一组。关闭窗口/Esc 仅隐藏画面。RRD 只保存数值与三维点，不含调试图像。SDL renderer 会打印 accelerated 或 software，NoMachine 下需要关注实际后端。

Rerun 原图像后端仍可切回：display.backend=rerun。该路径同帧共享 JPEG 压缩，但会给各模块提交图像，并为 HUD 编码整幅透明 PNG。后台异步不代表零成本；CPU、内存带宽、文件写入和 Viewer 渲染仍可能与推理竞争。提高显示上限到 60 Hz 只能解除人为限流，不会让推理自动达到 75 FPS。

固定滞后需分别量：曝光→算法结束、曝光→串口发送、曝光→本地显示、远程桌面附加延迟。应用的最新帧槽不能排除 SDK batching、Viewer 时间线播放位置、解码、渲染和 NoMachine 的延迟。Process FPS 高也可能一直显示较旧的帧。之前建议过临时设置 RERUN_FLUSH_TICK_SECS=0.01 做对照，未收到效果反馈，不能标成已修好。

SDL 尚无用户目标机同条件性能结果；不能承诺已经恢复 75 FPS。先做 debug 全关 / SDL / Rerun 三组各 60 秒，同场景、同分辨率、同模式、同精修条件；同时记录处理吞吐、显示吞吐、帧龄 P50/P95/P99、CPU/GPU、SDK 跳号和调试覆盖数。

## 7. SP、RMCS、深大后续看哪里

本地参考目录是开发证据，不把三套开源整仓塞进运行包。借鉴代码必须保留相应来源与许可证；当前来源记录在各模块 SOURCE/许可证文件。

- SP：sp_vision_25-main/tasks/auto_buff 的 detector、solver、target、predict、aimer，以及 src/auto_buff_debug。学习模块接口、角度跳变处理、预测时间和发弹节奏。它区分 Small_Predictor 等模型，不用其装甲板算法替换神符状态；buff_aimer.cpp 中还有局部 yaw/pitch 使用顺序需独立核查，不能机械照抄。
- RMCS：src/module/detector/rune.cpp、src/module/tracker/model/rune.cpp、src/kernel/fire_control.cpp、src/io/recorder。学习观测语义、PnP、关联/EKF、未来状态与记录。没有配套标定和姿态的数据不能用于验收其几何投影；出现错配时也不能仅因“上游没改”就排除实现缺陷。先用可复现数据区分移植差异、数值条件和标定误差，再决定改不改算法。
- 深大：RP-26Rune 的 NNDetector、RuneObservationRefiner、PowerRunePlane 和 RuneDecisionModule；RuneDetectionModel/NNDeployment 的模型协议。优先学习三类五点、局部轮廓选择、灯臂到板心的几何一致性，以及有效观测与允许输出的职责边界。当前网络没有检出的目标，精修无法凭空补出；模型适配、曝光和轮廓问题需分开定位。

## 8. 约 75 FPS：先消除实测瓶颈，再做模型优化

当前 CPU 同步纯推理平均 17.65 ms，对应约 56.7 次/秒，已经超过 75 FPS 的 13.33 ms 全链路预算。仅换显示库不能跨过这个限制。若以推理预算 10–11 ms、其他阶段 2–3 ms 为目标，这是待验证的分配，不是已测结果。

第一步：实机拆分预处理、infer、decode、判色/几何、track、shoot、报告写入、调试提交和曝光到发送的时间。汇总到每秒或文件，避免逐帧刷日志。记录 CPU 型号、P/E 核、频率/温度、相机分辨率、模型 SHA 和 OpenVINO 属性。当前 detect.tracy_debug 不会自行在 live 启动 Tracy 客户端，不能只打开 YAML 就声称采集到全链路。

第二步：固定同一模型，测试 2/4/6/8 线程、OpenCV与OpenVINO的线程竞争、精度属性和输入预处理；核实 iGPU 是否实际可用，再独立测试 GPU。当前生产代码硬编码 CPU，没有现成 device 配置入口。融合预处理、复用临时缓冲是候选优化，必须先量成本和核对 RGB/NCHW/归一化一致性。不要只靠增加线程或请求数来报高 FPS。

第三步：优先试 INT8 PTQ，标定数据包含红/蓝、远/近、大小符三类、暗场/过曝、遮挡与转场。除检出率外，核对每个端点、R 和恢复板心的像素误差，以及最终预测误差。PTQ 退化明显再做 QAT。当前包内默认是原 ONNX，不附带一个未经验收的量化模型。

第四步：确需改模型时才研究轻量骨干、重参数化和蒸馏，保持协议并重新训练导出。改网络分辨率会影响当前硬编码 [1,3,480,640] 和 [1,18,6300]，不能只改 YAML；跟踪 ROI 裁剪必须保留坐标还原、R 与灯臂覆盖、丢失后全图重捕获和尺度验证。

异步推理可重叠 CPU 预处理与设备计算，但单设备饱和后增加请求不一定降低单帧延迟；必须按曝光时间消费结果、限制在途请求，防止吞吐提高却使控制更旧。batch>1 不作为实时瞄准首选。跳帧后 track 的外推频率不能冒充检测频率。

### 论文调研与本工程的对应关系

以下根据原论文公开页面和方法说明整理，尚未在本工程移植验证。不同论文的手机/GPU成绩不外推到本机 Intel CPU。

| 论文 | 核心启发 | 本工程如何验证 |
|---|---|---|
| [ShuffleNet V2, ECCV 2018](https://arxiv.org/abs/1807.11164) | FLOPs不足以代表速度；访存、算子碎片和目标平台都影响延迟 | 看逐层耗时和中间张量搬运，先定位 reshape/concat/resize 等开销；不凭参数更少就换模型 |
| [MobileOne, CVPR 2023](https://arxiv.org/abs/2206.04040) | 按实际设备延迟设计骨干，并用重参数化简化部署结构 | 若推理长期占主导，再测试兼容姿态头的轻量骨干；论文 iPhone 的毫秒数不是本工程承诺 |
| [RepVGG, CVPR 2021](https://arxiv.org/abs/2101.03697) | 训练多分支，部署融合为简洁卷积结构 | 对已采用可融合结构的自训练模型验证导出前后数值；任意现有 ONNX 不能无条件变成 RepVGG |
| [Jacob 等, CVPR 2018](https://arxiv.org/abs/1712.05877) | 整数推理与配套训练兼顾效率和精度 | 先做 PTQ 基线，端点精度不足再用 QAT；核对真正执行 INT8 的算子覆盖率 |
| [Hinton 等, 2015](https://arxiv.org/abs/1503.02531) | 把较强模型知识迁移到小模型 | 自训练时让教师指导类别及关键点；姿态蒸馏损失需另外设计，原文不是神符关键点方案 |

实施顺序：SDL实测与全链路计时 → 同权重CPU参数/预处理对照 → INT8精度与速度 → 轻量模型/蒸馏。标定、时间同步、遮挡后重捕获和打符命中验证与性能测试并行推进。
