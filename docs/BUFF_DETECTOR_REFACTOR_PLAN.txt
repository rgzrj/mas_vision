打符检测模块重构方案
日期 2026-11-20

一、整体目标

将 BuffDetector 改为抽象检测基类，通过静态工厂创建 YoloDetector 或 TraditionalDetector。上层业务只持有 BuffDetector 的智能指针，通过 submit 和 collect 完成检测。

工厂在一次检测器创建过程中读取一次业务 YAML，基类和子类从同一份内存节点提取参数。代码保持直接、整洁、易读，沿用装甲板模块的代码风格。

二、类型与文件安排

buff_types.hpp 保存 EnemyColor、RuneMode、Board、RuneIcon、LightArm 等基础数据类型。

完整的单帧结果定义为 BuffDetector 内部公开的 Detection 结构体。沿用现有结果字段，包括模式、R 标、符板、激活灯臂、原始关键点和可选二值掩膜。外部统一使用 BuffDetector::Detection。

buff_detector.hpp 声明抽象基类、嵌套结果类型及静态工厂。buff_detector.cpp 实现工厂、公共参数解析和公共检测流程。

YoloDetector 与 TraditionalDetector 分别继承 BuffDetector。现有 DetectionBackend 和外层转发式 BuffDetector 合并为这一个基类，删除迁移后失去用途的转发代码。

三个头文件之间保持清楚的单向依赖。基础类型头文件不依赖检测器，检测器引用基础类型，跟踪及调试模块根据需要引用嵌套结果类型。

三、业务配置组织

继续使用现有 auto_buff.yaml。检测配置集中在 auto_buff.detect 下，划分为 backend、common、yolo、traditional。

backend 选择本次启动的算法后端。common 保存检测颜色和检测 debug 等真正共有的参数。yolo 保存模型、设备、线程数、置信度、关键点阈值和精修方式等专属参数。traditional 保存传统视觉专属阈值及几何筛选参数。

现有 track、shoot、runtime、display 配置保留各自职责。迁移字段时保留原有默认值、单位和行为。nms_distance 继续表示原图像素距离。

只解析当前选定后端的专属分段，未启用后端的配置段缺失时仍可正常创建。

四、静态工厂与单次读取

上层传入业务 YAML 路径，调用 BuffDetector::create，取得 std::unique_ptr<BuffDetector>。

create 内直接读取业务 YAML，得到内存根节点，再读取 backend 并构造对应子类。子类构造函数接收只读节点引用和必要的资源目录。

模型相对路径通过配置文件所在目录解析。业务 YAML 路径只在创建入口使用，基类构造函数和子类构造函数均不读取业务配置文件。

这里的单次读取针对一次检测器创建过程。当前相机标定仍位于独立的 hikcamera.yaml，传统检测需要时由初始化入口额外读取一次，并传入标定节点。子类只使用准备好的内存数据。

构造过程中将需要的参数取出并保存，避免通过引用持有工厂局部节点。

五、基类职责与权限

BuffDetector 的受保护构造函数解析 common 节点，完成公共成员赋值和检测调试初始化。

颜色及调试状态放在基类 private 内。子类通过少量受保护接口读取必要的公共状态。颜色设置接口只接收 EnemyColor 枚举，函数体直接赋值。

基类提供虚析构函数，禁用拷贝构造和拷贝赋值。资源通过成员对象和智能指针管理。

后端已经由具体对象类型确定，通常无需在基类重复保存 backend 字符串。

六、子类初始化

YoloDetector 先调用基类构造函数，再从 yolo 节点读取自己的参数，解析模型路径，检查模型协议，初始化选定设备及推理资源。OpenVINO 对象和推理请求由 YoloDetector 持有。

TraditionalDetector 先调用基类构造函数，再从 traditional 节点及传入的标定节点初始化传统视觉资源。

子类专属成员使用 private。基类不保存设备、模型路径、YOLO 阈值或传统视觉专属参数。

七、统一执行接口

对外统一提供 submit 和 collect 两个执行操作。上层不判断 CPU、GPU 或传统后端，不接触推理请求、槽位及单独的请求管理对象。

submit 接收本帧图像及对应的时间、模式和最终颜色等配对信息。成功接收返回 true；槽位已满返回 false，不消耗本次输入、不覆盖已有请求，也不改变已接收帧的顺序。调用方确认接收成功后，才移除输入队列中的这一帧。

collect 只收取最早提交的一帧。没有待收取帧，或最早请求尚未完成时，返回 std::nullopt，不阻塞等待推理完成。取得完成结果后，在调用线程内进行后处理、公共过滤和检测调试提交。

未检出目标仍是一次完成的检测，交付空观测的 Detection；std::nullopt 只表示当前没有可交付结果。执行失败通过异常报告，不伪装成满槽或未完成。

CPU 和传统后端在 submit 中完成计算并暂存结果，在 collect 中交付。GPU 后端在 submit 中启动异步推理，在 collect 中交付已完成结果。所有后端遵守相同的接收、拒收和收取约定。

交付时同时提供对应帧的信息，复用已有帧数据组织。跟踪、解算和调试均使用结果所属帧的图像、曝光时间、姿态、模式及颜色，不能套用调用 collect 时的新帧信息。

已接收图像在结果收取或退出清理前保持只读，检测器持有必要的图像引用。需要直接修改像素的调试绘制使用副本，图元叠加继续采用现有方式。

八、模式与颜色处理

router 统一解释 MCU mode 与 YAML 颜色配置，确定当前任务和最终识别颜色，并随帧传给对应算法线程。

接入裁判系统时，MCU 发送转换后的 0～5，YAML 颜色配置为 red，采用现有协议的红蓝映射。

未接入裁判系统时，MCU 发送 0、2、4，通过 YAML 颜色字段选择检测红色或蓝色。

具体映射采用已讨论的规则。0、2、4 使用 YAML 颜色，1、3、5 使用蓝色。原始 MCU mode 随帧保留。

算法线程通过枚举 setter 应用最终颜色。检测器内部负责按该颜色检测或过滤结果。

submit 成功时保存该帧最终颜色，后续切色不改变已接收帧的颜色。模式同样按提交时的帧信息保存。

九、调试对象归属

检测调试对象在 BuffDetector 内部初始化，受检测 debug 配置控制。

跟踪和解算调试对象由各自模块持有。跨三个阶段的帧时间、布局和整帧提交由调试协调层管理。

检测绘制在算法线程调用 collect、处理对应完成帧时执行。推理完成通知不承担绘制或显示工作，窗口事件和渲染继续由现有 Display 路径处理。

对外头文件仅包含必要的图像和结果类型。YAML::Node 使用前置声明，yaml-cpp 在实现文件中引入，OpenVINO 类型留在 YOLO 实现范围内。

十、队列与 GPU 请求管理

线程之间继续使用项目已有的 rigtorp::SPSCQueue。使用 try_push 表达满时拒收，保持单生产者、单消费者约定，不新增队列依赖。

YOLO 内部固定复用两个请求槽位。submit 和 collect 由同一算法线程调用，保留 std::array<Inference, 2>、head_ 和 pending_ 管理槽位，通过 OpenVINO 查询请求完成状态，无需再引入内部并发队列、future 或额外工作线程。

每个槽位持有独立的推理输入及对应帧信息，预处理缓冲在推理结束前不得释放或被下一帧改写。请求及输出缓冲在后处理完成前不得复用。

严格按提交顺序收取。collect 只检查 head_ 指向的请求；后一帧先完成时继续保留，不能越过前一帧交付。并发队列的 FIFO 只保证入队顺序，不能代替这项请求顺序管理。

pending_ 表示已接收但尚未收取的帧数。推理完成但结果尚未收取时仍占用槽位，不能提前释放接收额度。成功收取并完成后处理后，再推进 head_、减少 pending_。

全部后端共用 BuffDetector 抽象接口和 BuffDetector::create 静态工厂。CPU／GPU 的配置解析、选择和推理资源管理全部归 YoloDetector，线程不再依赖 streaming、asynchronous、ready 或 can_accept_frame 等后端状态接口。

十一、失败与退出处理

配置解析、模型加载或设备初始化失败时，构造过程抛出异常。create 集中记录错误并返回空指针，上层判空后结束启动。

日志初始化先于检测器创建。运行中的异常交给现有线程异常出口处理。

退出时先结束使用检测器的工作线程，再销毁检测器。YOLO 完成自身在途请求的资源收尾。

十二、实施顺序

第一步，整理基础类型，将完整结果移入 BuffDetector::Detection。

第二步，建立抽象基类和静态工厂。

第三步，将公共配置解析、颜色及模式过滤和检测调试放进基类，建立 submit、collect 的统一契约。

第四步，将两个子类构造函数改成接收内存节点及必要资源位置。

第五步，清理迁移后失去用途的转发层、重复成员和重复文件读取。

第六步，同步线程、跟踪、调试、回放、工具及测试。

第七步，分别验证两个后端启动，确认未启用后端的配置段可缺失。

第八步，用相同输入对照检测数量、坐标、颜色与模式过滤结果。

第九步，验证满槽拒收、拒收不消耗输入、未完成返回空、未检出目标仍交付结果，以及收取后释放槽位。

第十步，验证后一请求先完成时仍按 FIFO 交付，并检查图像、曝光时间、姿态、模式和颜色的配对关系。

第十一步，验证失败退出及在途请求的资源释放。性能对照使用相同输入和配置，检查处理帧率、CPU 占用及结果时延。

十三、整洁性与可读性要求

命名沿用已有领域术语，函数承担清楚的单一职责。相关变量集中排列，同层声明适度对齐，不同职责之间留空行，大括号风格统一。

注释简短说明单位、坐标、资源生命周期和必要约定。配置读取直接表达，避免为少量判断增加独立包装函数。

修改时保持现有算法结果、点序、坐标单位和时间含义一致。
