# 串口、模式路由与检测器封装设计草案

更新日期 2026-11-19

本文记录讨论方案和分批实施进度。具体完成项见文末，其余建议和待确认项仍待实施，当前源码以实际文件为准。

## 1. 本次整理目标

- 以 mas_vision-main 的串口实现为模板重新整理，由 router 统一解释 MCU 已转换的 mode 和检测颜色。
- 未使用电控颜色时，通过 YAML 设置检测颜色。
- router 将实际任务、检测颜色和对应模式状态随帧投递，算法线程应用该颜色。
- 打符业务统一通过 BuffDetector 构造检测器。
- 检测基类改名，清楚区分业务入口与具体后端。
- 代码必须整洁、易读，沿用原版风格；命名简明准确，同层代码适度对齐，不同职责之间留空行，函数职责单一，注释简而精。

## 2. 已核对的现状

### 2.1 颜色传递

当前 router 读取两份业务 YAML，计算颜色后随 VisionFrame 投递。

armor_thread 当前使用 ArmorDetector_Set_Color(EnemyColor)，在模式版本变化时设置颜色并记录日志。

第二批已将 Buff 业务入口改为 BuffDetector_Set_Color(EnemyColor)，线程参照装甲板显式判断红蓝并传入枚举。配置颜色在读取处直接判断并校验。同步和 GPU 路径的调用时机沿用原实现。

两边业务入口采用相同命名风格与枚举入参。装甲板和 Buff 分别使用各自命名空间下的 EnemyColor，Buff 保留 UNKNOWN 表达未确定的观测颜色。

YOLO GPU 提交图像时保存对应颜色，收取时使用保存的颜色。后续切色不会改变已经提交的图像所使用的颜色。

### 2.2 已明确的通信链路

裁判系统信息由 MCU 处理，MCU 向视觉端发送转换后的 mode。视觉端依据双方约定解释该 mode。

mas_vision-main 的 receiveSerial() 将 packet.mode 映射为 VisionMode，原版装甲板线程根据接收状态和模式变化更新检测颜色。

hasReceivedData() 表示收到过有效 MCU 数据，重连时会清零。它本身不表达裁判系统的连接状态。

原版 last_mode 初始化为 0，因此启动后一直收到 0 时不会触发切色，YAML 初始颜色得以保留。该行为需要与真正的颜色来源约定分别核对。

### 2.3 当前模式定义

| mode | 当前枚举 | 含义 |
| --- | --- | --- |
| 0 | AUTO_AIM_RED | 自瞄红色 |
| 1 | AUTO_AIM_BLUE | 自瞄蓝色 |
| 2 | SMALL_RUNE_RED | 小符红色 |
| 3 | SMALL_RUNE_BLUE | 小符蓝色 |
| 4 | BIG_RUNE_RED | 大符红色 |
| 5 | BIG_RUNE_BLUE | 大符蓝色 |

当前 router 为兼容固定 2／4 与 YAML 调色，使用了初始颜色及模式最低位变化规则。后续由 router 按 MCU 模式约定统一处理颜色，固定 0／2／4 的 YAML 调色要求仍需覆盖。

## 3. 串口与 router 职责方案

### 3.1 职责安排

| 位置 | 计划职责 |
| --- | --- |
| user_serial.cpp | 以原版为模板解析 MCU 数据，提供 mode、姿态和通信状态，管理发送快照 |
| vision_router.cpp | 统一处理 MCU 模式与颜色，投递实际任务、检测颜色、模式状态与配对姿态 |
| armor_thread.cpp | 应用本帧路由状态和颜色，运行装甲板算法，作为线程风格基准 |
| buff_thread.cpp | 按装甲板线程风格组织流程，运行打符算法，GPU 请求保存提交时颜色 |
| 检测器 | 构造时读取业务配置，保存并应用调用方传入的颜色 |

router 中的模式分支采用直接、易读的 if / else if 或 switch 写法，算法线程通过 setter 应用结果。

两个算法线程启动后持续存在，router 根据 mode 改变帧的投递方向。

随帧携带颜色用于说明本帧的检测上下文。当前装甲板在模式版本变化时设置颜色，Buff GPU 在提交时设置颜色；本轮保留这些调用时机。重复赋值本身不创建推理请求或重载模型，切色日志只在实际更新时记录。

GPU 请求需要保存每次提交时的颜色，保证旧请求收取时仍使用对应颜色。

串口实现以 mas_vision-main 为模板整理。VisionCommand 的独立封装、重复转发和重连清理需要重新评审，旧模式及过期结果的失效保护集中在内部管理。

### 3.2 MCU 模式与 YAML 调色约定

用户已明确，接入裁判系统后 MCU 发送转换后的 0～5，视觉端将 YAML 颜色配置为 red 即可。

未接入裁判系统时，电控发送 0／2／4，通过 YAML 颜色字段改变识别颜色。该要求同时覆盖装甲板、小符和大符。

按以上要求，草案建议采用以下确定规则，供用户评审。

| MCU mode | 任务 | YAML 为 red | YAML 为 blue |
| --- | --- | --- | --- |
| 0 | 自瞄 | 检测红色 | 检测蓝色 |
| 1 | 自瞄 | 检测蓝色 | 检测蓝色 |
| 2 | 小符 | 检测红色 | 检测蓝色 |
| 3 | 小符 | 检测蓝色 | 检测蓝色 |
| 4 | 大符 | 检测红色 | 检测蓝色 |
| 5 | 大符 | 检测蓝色 | 检测蓝色 |

此表中 YAML 为 red 时完整保留当前 0～5 的红蓝映射；YAML 为 blue 时覆盖 0／2／4 的检测颜色。原始 MCU mode 仍随帧保留。

上述规则已在 router 中落实，接裁判时 YAML 使用 red。

YAML 在启动时读取，修改后重启生效。

### 3.3 原版写法需要处理的边界

- 原版启动时保持 mode=0 会沿用 YAML；整理时须保留要求的手动调色能力，并核对模式变化后的行为。
- router 给本帧确定的 mode、任务和颜色保持一致，算法线程使用同一份随帧状态。
- 若把原版非活动分支中的无参数 disableVision() 原样放回双线程，可能撤销另一线程的有效输出。当前带模式状态的撤销已有来源检查，后续整理须保留这项约定。
- GPU 请求保存提交时的颜色，收取结果时沿用对应颜色。
- 核对 router 中的颜色变量、VisionFrame.color 及录制回放调用，保留各自明确的用途。

## 4. BuffDetector 内部封装方案

### 4.1 统一业务构造

实机、回放和普通测速统一采用下面的构造方式。

```cpp
auto_buff::BuffDetector detector(config);
```

BuffDetector 根据 YAML 选择 traditional 或 yolo。YOLO 再根据 device 选择 CPU 或 GPU。

模型协议检查等专项测试仍可直接构造具体后端。

### 4.2 类型命名

检测基类已改名为 DetectionBackend，相关继承和调用已同步。

```text
BuffDetector
    └── 持有 DetectionBackend
            ├── TraditionalDetector
            └── YoloDetector
```

| 类型或目录 | 职责 |
| --- | --- |
| BuffDetector | 统一构造与业务调用入口 |
| DetectionBackend | 共用单帧检测接口、颜色状态、观测过滤和调试绘制 |
| TraditionalDetector | 传统检测实现 |
| YoloDetector | YOLO 检测流程装配 |
| yolo/inference | CPU／GPU 初始化与推理请求管理 |
| yolo/observation | 模型输出转换为公共观测 |
| yolo/pixels | 角点精修 |
| detection.hpp 中的观测类型 | 描述检测结果，供后续模块使用 |

基类声明是否从 detection.hpp 移入内部头文件，后续根据头文件依赖决定。

### 4.3 构造时完成后端装配

后端选择已集中到 buff_detector.cpp 的一个装配点，构造时取得具体 YOLO 对象，已去掉 dynamic_cast。

BuffDetector 构造和现有独立后端工厂复用该装配点。

现有回放和独立测试仍使用 make_detector()，该入口保留，统一复用后端装配。

现有窄范围 friend 可以继续使用。是否增加独立 StreamingDetector 接口，待真实需求确认。

### 4.4 同步与异步调用

同步入口继续提供 detect()，返回对应输入图像的完整检测结果。

异步调用保留提交、就绪查询、收取和丢弃的阶段。GPU 请求、张量、槽位和资源回收由 YOLO 内部维护。

需要明确的约定如下。

- 非流式后端的 frame_ready() 返回 false。
- GPU 没有待收取图像时，frame_ready() 返回 false。
- 同步 detect() 与在途异步请求交错使用时，保留明确的错误检查。
- 图像像素在对应请求收取或丢弃前保持有效且只读。
- 曝光时间、姿态和模式元数据与检测结果保持对应。

附件提出的帧标识 token、mode 捕获时机和 OpenVINO 头文件隔离仍属待评估项，具体范围由后续评审确定。

## 5. 建议的分步顺序

1. 对照原版串口模板及 MCU 已转换的 mode，明确固定 0／2／4 的 YAML 调色规则。
2. 整理串口与 router，统一模式和颜色处理，核对算法线程及录制回放的使用方式。
3. 将 Detector 重命名为 DetectionBackend，更新继承、指针和测试引用。
4. 将后端装配集中到 BuffDetector，统一回放与普通测速的构造入口。
5. 根据实际需要再确定异步配对接口的调整范围。

每一步分别检查差异，便于评审和回退。

## 7. SP 对照补充

核查对象为本地 sp_vision_25-main 的 standard_mpc.cpp、mt_standard.cpp、多线程检测器和 CommandGener。

### 7.1 帧信息

所查 SP 流程没有 VisionFrame 这一类型。

多线程检测器通过 tuple 将图像、时间戳和 InferRequest 放进同一队列，取得结果时返回对应图像、检测结果及时间戳。

当前 VisionFrame 将图像、时间、模式状态、颜色及配对姿态集中为具名字段。是否精简字段应逐项核对使用处，保持异步结果与输入信息对应。

### 7.2 颜色

SP 所查自瞄流程由 Tracker 构造函数读取 enemy_color，跟踪时按该颜色过滤装甲板。所查主入口没有根据 mode 每帧更新颜色的流程。

SP 的 GimbalMode 区分空闲、自瞄、小符和大符，颜色与本项目 0～5 的模式编码约定不同。

### 7.3 休眠和非活动状态

| SP 路径 | 读取到的实际行为 |
| --- | --- |
| standard_mpc.cpp 的规划线程 | 自瞄且有目标时每轮休眠 10 ms，其他情况休眠 200 ms |
| standard_mpc.cpp 的业务主循环 | 自瞄与打符按分支执行，空闲分支发送不控制指令 |
| mt_standard.cpp 的检测线程 | 非自瞄时直接 continue，该分支没有休眠 |
| mt_standard.cpp 的业务主循环 | 处理自瞄或打符，其他模式直接 continue |
| CommandGener | 每轮休眠 2 ms；使用 200 ms 内的输入，该类未读取当前业务 mode |
| ThreadSafeQueue::pop | 空队列时通过条件变量等待 |

休眠用于控制空转占用，结果验收用于处理已经开始的计算，两者解决不同问题。

当前工程的两个算法线程空队列时已休眠 1 ms。后续是否改为阻塞唤醒应单独评估。

## 8. RMCS 对照补充

核查对象为本地 rmcs_auto_aim_v2-main 的 component.cpp、kernel/auto_aim、kernel/detector 和 utility/image/image.hpp。

### 8.1 颜色与模式

组件层通过遥控器、键盘和导航请求更新 Context.track_rune，通过裁判系统输入更新 Context.id。

图像处理开始时加锁复制 Context，本帧处理使用这份快照。

在机器人身份已知时，每帧调用 update_detect_color()，随后调用 update_detect_rune() 决定检测装甲板或符。

update_detect_color() 内部更新颜色字段及符检测器配置，未在此处重建模型或输出切色日志。每帧调用 setter 与每帧产生重配置开销需分别判断。

该本地版本对符检测配置还进行了颜色取反，其颜色约定需要沿调用链理解。本工程继续按自身 MCU 协议确定检测颜色。

### 8.2 帧数据与处理状态

RMCS 使用 Image 包装 CameraFrame，访问图像、曝光时间、曝光姿态及接收和发布时间。

模式和身份放在单独的 Context 中，在本帧开始处理时读取。所查 Image 接口不携带 mode 或颜色字段。

当前 VisionFrame 同时携带帧数据和路由状态。两种组织方式均需保证图像与自身姿态、时间戳对应；模式状态的采样时刻则有所不同。

### 8.3 等待、输出和切换边界

相机回调发布最新帧并 notify_one()。图像工作线程没有可处理帧时调用 atomic::wait()，收到新事件后唤醒。

同一个图像工作线程根据本帧 Context 选择检测分支，因此所查路径没有两个算法线程互相撤销输出的结构。

组件层维护当前跟踪目标，目标时间超过 100 ms 时清除并关闭有效输出。

所查路径未发现等价于本工程 mode + epoch 的结果验收，不能由统一工作线程推断所有跨模式在途结果都会被拒绝。实际电控通信驱动位于外部组件，重连策略未在此仓库完整核实。

## 9. 当前确定的设计取舍

- MCU 协议沿用当前约定。接裁判时颜色配置为 red；未接裁判且发送 0／2／4 时可用 YAML 调整检测颜色。
- 装甲板和 Buff 保持对称，以装甲板线程为风格基准，统一构造、变量排列、颜色接口和主循环的阅读顺序。
- 保留 VisionFrame。具名字段便于阅读图像、姿态、时间和路由状态的对应关系，后续整理字段分组、初始化排版和必要注释。
- 保留当前颜色更新时机。相同颜色的重复赋值成本很小，当前未测得它造成性能问题。GPU 请求保存对应颜色，切色日志避免逐帧输出。
- 保留两个算法线程空队列时的 1 ms 休眠。事件等待能减少长时间闲置唤醒，但需要配套通知和退出处理，当前没有测量结果要求改变等待机制。
- 旧模式结果的验收、串口内部整理及 MCU 模式与 YAML 颜色约定，继续按前述章节评审。
- 按用户要求分批实施，每批记录范围和验证结果，便于逐项评审。

### 9.1 整洁性与可读性要求

两条线程按相同顺序组织代码。

1. 日志与配置路径。
2. detector、tracker、shooter 和 debug 对象。
3. 串口引用及线程状态。
4. 取帧、模式状态与时间有效性检查。
5. 状态切换与颜色应用。
6. 检测、跟踪、解算及结果提交。
7. 退出日志。

GPU 提交、就绪查询和收取等专有步骤集中放置，各步骤与对应帧的关系明确。

相关变量集中声明并适度对齐，不同职责之间保留空行；检查失败后尽早结束本轮处理，减小嵌套深度；注释简短说明用途和约定。

具体接口命名沿用装甲板现有风格。整理时逐项检查调用方，保持算法输出和资源生命周期一致。
