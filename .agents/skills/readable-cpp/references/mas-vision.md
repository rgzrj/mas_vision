# MAS 视觉工程约定

仅在确认当前代码属于 MAS 视觉工程时使用。可用 apps/main.cpp、threads/vision_router、auto_buff/buff_detect/buff_detector.hpp 等路径核对，不能只凭目录名称判断。
这些是用户已确认的项目边界，不是通用 C++ 规范；当前明确指令优先。路径和接口可能继续演化，修改前仍需核对源码。

## 算法与调度

- 线程可以依赖 detect、track、shoot 和 debug 公共接口；不要直接依赖 YOLO 推理、像素精修或跟踪模型内部实现。
- 保留 ArmorDebug、BuffDebug 在线程内协调帧边界和布局；业务绘制由各模块的调试实现维护。不要借封装重构移除已确认的 debug 使用方式。
- BuffDetector 是传统检测与 YOLO 的统一入口。使用既定 create 与 submit/collect 契约，内部实例化 YoloDetector 或 TraditionalDetector。
- 业务 YAML 由检测工厂读入，基类与后端从内存节点提取参数；相机标定是独立资源，不强行并入同一配置载体。
- Inference 管理内部请求、CPU/GPU 资源和在途上下文；线程不另行构造 YoloRequests，不通过 dynamic_cast 调用特定后端。
- OpenVINO/TensorRT 的构建选择和 YAML 的运行设备选择属于不同层次，按当前实现核实，不随意改成插件注册体系。
- 已确认沿用 RMCS 的算法流程、状态含义和关键数学约定；排版或封装任务不授权替换算法。对齐上游时核实源码，不凭印象推断。

## 帧、模式和指令

- VisionFrame 与工作队列定义继续归属现有 vision_router.hpp，不新增 threads/vision_types.hpp。
- 优先使用串口已有 VisionMode 及 state.mode 路由，避免恢复冗余 VisionTask；算法内部 RuneMode 有自己的语义，可以保留。
- 图像、曝光姿态、时间和模式版本成对传递。异步收取使用提交时的信息，不能混用当前颜色、姿态或新模式。
- 当前颜色约定：0/2/4 沿用 YAML 配置，1/3/5 选择蓝色；接裁判系统时 YAML 设 red。模式与颜色策略留在调度/线程层，检测器负责应用颜色，不自行读取串口模式。
- VisionCommand 属于调度层，串口负责接收模式与姿态及收发协议包。保留模式版本、重连、过期和旧结果验收约束。
- 模式失效、无姿态或无解等撤销路径只撤销有效标志与开火建议，保留最后一次目标角度；不能用全零包替换无目标结果。
- 不恢复非活动算法线程对全局指令的无条件清空，旧帧不能撤销另一活动模式的指令。

## 时间、显示与性能

- 实机火控使用真实处理时刻；回放使用记录/媒体时刻。暂停、单步和回放速度不应改变同一记录的预测提前量。
- SDL 与 Rerun 各自维护后端，通过 YAML 选择初始化路径；debug 控制窗口和调试数据。未选中的后端不初始化。
- 保留当前 SDL 30 fps 显示上限和最新帧策略；显示采样不限制算法处理频率，不擅自给生产检测增加 120 fps 节流。
- OpenCV 线程数由进程统一设置；OpenVINO 推理线程单独控制，不由两个检测器竞争修改进程级设置。
- 业务诊断、初始化信息和运行统计使用现有日志入口；帮助文本按 CLI 需求处理。日志应先于算法构造初始化，退出收尾晚于生产者结束。
- 录制/回放保留独立应用编排并复用生产算法；不要为减少表面重复，擅自合并成新的统一 Pipeline。
- tests 检查模块逻辑；人工设备诊断、模型测速和 plot_monitor.py 等工具归 tools。
