# 可读 C++

写给人阅读和维护的代码：上层调用清楚，内部职责明确，必要的状态与约束完整。
精简不等于压缩排版；封装不等于增加层数；统一接口不等于只有一个方法。

当前用户要求和仓库规则优先。本技能约束本次任务，不授权扩大修改范围。
确认当前仓库是 MAS 视觉工程后，再读取 [项目约定](references/mas-vision.md)；其他工程不套用这些业务约定。

## 1. 先读调用链，明确改动类别

- 修改前读入口、调用方、实现方和相关测试，确认状态归属、资源生命周期及同步/异步契约。
- 以当前源码为依据，核实历史报告与文档；不声称已经阅读或验证未检查的部分。
- 区分排版整理、结构重构、行为修改。只要求空行、对齐和美观时，不改算法、时序、参数、异常策略或返回语义。
- 用户要求先思考、先讨论、先评估时，只提供具体方案，不写文件。
- 优先沿用经过验证的原版结构。每处改动应能对应本次要求，不顺带改名、清理或重排无关代码。

## 2. 对外提供稳定的业务入口

- 每个子系统向调用方提供统一的业务入口；后端替换不要求上层重新组织算法流程。
- 构造函数或既定工厂负责初始化，成功后对象即可正常使用。不要额外暴露请求管理器才能获得完整能力。
- CPU/GPU、厂商 SDK、槽位和缓冲区留在实现内部；业务调用方不通过类型转换判断后端再分别调用。
- 必要的方法组合可以属于同一接口，例如 submit/collect。明确阻塞行为、结果对应哪帧、顺序和失败含义，不为方法数少而隐藏等待或更换结果语义。
- 公共头文件暴露必要类型和契约，私有实现头文件不成为上层依赖。根据实际收益隔离 SDK，不强制所有类使用 Pimpl。

## 3. 封装必须承担实际职责

- 类管理自己拥有的状态、资源和不变量；基类仅管理真正共有的内容，专属配置与资源由实现持有。
- 不为形式增加基类、管理器、注册表、配置载体或一组空转发接口。
- 一行转发若承担接口适配、隐藏后端或统一契约的作用，应保留；删除前说明它实际没有承担什么职责。
- 拆分依据是职责、独立变化和复用需求，不是固定行数。避免一个巨类管理所有事务，也避免把连续流程拆成大量小文件。
- 先查现有实现，再考虑标准库、平台能力和已有依赖；不为少量直白代码引入新依赖或通用框架。

## 4. 配置与数据各有归属

- 同一模块在合适入口读取业务 YAML，内部传递内存节点，按需解析自身参数；不反复打开同一文件。
- 只校验当前启用后端的专属配置，相对资源路径统一按配置文件所在目录解释。该要求不是全程序只能读一次配置。
- 配置字符串在边界完成校验和转换；运行时优先使用已有类型。一次简单判断不必另加公共解析函数或多个 setter 重载。
- 新增结构体、枚举、状态字段前查找现有定义。同一语义保持单一来源，可直接推导的信息不重复保存。
- 避免冗余成员和重复保存依赖：已有成员对象提供所需参数时，不再单独保存同一参数的引用或指针；优先统一依赖入口，减少重复初始化和同步维护。整理前确认生命周期及更新语义，不为消除重复而新增包装层。
- 区分结构冗余与数据复制：引用、指针或 cv::Mat 浅拷贝不等于复制底层数据；是否保留取决于职责和有效期，不能仅凭同名字段判断冗余。
- 模块专用类型留在所属模块或类附近；真正跨模块的数据才进入公共定义。不要为集中而增加巨大的 types 文件。
- 最终结果、在途上下文和滤波状态用途不同，不能仅因字段相似就强行合并；不同领域的同名概念也不自动合并。
- 只供显示使用的名称转换、文字排版和图元逻辑放在调试实现中。

## 5. 函数流程直接，命名适量

- 函数围绕一个清楚的操作展开。优先处理无效输入和无需处理的情况，减少深层嵌套，让主流程容易找到。
- 控制成员访问层级，避免为统一数据而形成层层包装和长访问链。反复使用的深层成员可绑定清楚的局部 const 引用；这种局部别名不等于重复保存依赖，不必机械删除。
- 同一层级的流程放在一起，业务编排不混入设备操作、张量搬运或底层数学细节。
- 不为每几行代码增加函数、lambda、命名空间或文件；提取操作须实际改善理解、复用或测试。
- 名称只包含当前上下文需要的信息，避免重复堆砌模块名。数学中的 x/y/z、dt 等可以保留。
- 沿用项目命名。局部修改不进行全仓风格迁移；同类模块保持职责对称，允许执行方式存在必要差异。

## 6. 空行、对齐和注释体现层次

- 优先遵循仓库 .clang-format 和邻近约定。没有项目规则时，采用用户偏好的四空格缩进、Allman 花括号和约 120 列宽度。
- 配置读取、参数校验、资源初始化之间留一行；取帧、状态检查、算法计算、结果提交之间留一行。
- 同组连续赋值适度对齐，长表达式按语义换行；不跨无关代码块强行对齐，不把多个操作挤在一行。
- 不堆连续空行，不以缩短文件为由取消逻辑分组。仅格式化本次涉及范围。
- 注释简而精，遵循已有语言和格式；在中文工程中优先简短中文。说明原因、单位、坐标系、点序、所有权、失效条件与有效期，不逐行翻译代码。
- .hpp 说明接口如何使用，需要时采用 @brief/@param/@return/@note；.cpp 说明实现中的关键原因。不为显然的访问器补冗长注释。

## 7. 精简保留正确性与性能契约

- 不删必要的边界校验、资源收尾、错误传播或并发同步，也不在每层重复校验已成立的不变量。
- 初始化失败不能留下半可用对象。既定工厂若返回空指针，调用方必须处理；避免逐层重复记录同一异常。
- noexcept 按真实异常契约决定，不把它视为通用提速标记，也不机械地批量添加或删除。
- 异步图像、时间、颜色、模式和输出必须对应；明确 FIFO、满槽拒收、数据有效期，以及“尚未完成”和“完成但无目标”的区别。
- 不随意增加逐帧配置读取、整图复制、编码、日志或同步等待；复制是否必要取决于所有权和生命周期。
- 性能结论说明测量条件、吞吐和延迟，必要时检查 CPU 占用、波动与降频。未经测量不承诺性能收益，不把显示刷新限制直接套到算法频率。

## 8. 交付可查看、可验证的改动

- 按能独立说明目的和验证的批次修改，保持 diff 集中。讨论时说明实际改动点，不先构建未要求的框架。
- 逻辑变化运行针对行为的必要回归，优先复用已有测试；不写仅复述实现或锁定排版的测试。
- tests 放可断言的逻辑回归；人工预览、设备诊断和测速入口放 tools。
- 交付说明实际变更文件、解决的问题、已做验证和限制。区分源码检查、编译、模拟测试及实机验证。
- 参考开源时核实具体契约，说明哪些原则适用于当前问题，不把其他项目的排版或架构整体移植过来。

## 参考依据

以下资料用于解释原则，不要求每次任务重新浏览，也不覆盖用户和仓库的具体约定。

- [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)：接口契约、减少实现暴露、函数职责与资源管理。
- [LLVM Coding Standards](https://llvm.org/docs/CodingStandards.html)：库分层、私有头文件、提前返回和阅读负担。
- [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html)：自包含头文件、命名及接口/实现注释的分工。
- [rigtorp/SPSCQueue](https://github.com/rigtorp/SPSCQueue)：集中在一个类型中的配合操作与明确的数据有效期；不是要求业务模块一律采用其队列实现。
